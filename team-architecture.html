始终用 feature 分支

绝不让 AI 在 main 上直接工作

AI + 人协同审查

AI 审代码细节（语法、边界、安全），人审架构和原理（设计模式、业务逻辑、可维护性）

AI 可推 feature 分支，不可推 main

AI 可以在 feature 分支上推代码、创建 PR；main 必须通过 PR 合并，禁止直接推送

AI + 人协同 Review 模型

🤖 AI 负责（代码细节）
  • → 语法错误、拼写错误
  • → 边界条件、空值处理
  • → 安全漏洞（SQL 注入、XSS）
  • → 代码风格一致性
  • → 幻觉 API（不存在的函数）
  • → 测试覆盖率
  • → 依赖合理性
👤 人负责（架构 & 原理）
  • → 设计模式是否正确
  • → 业务逻辑是否符合需求
  • → 模块间耦合是否合理
  • → 可维护性和扩展性
  • → 性能瓶颈风险
  • → 是否符合团队约定
  • → "这样做对不对"
💡 关键点
人不需要逐行看代码。AI 先跑一遍 review 输出报告，人只看架构层面的决策是否正确。不懂代码的人也能审——因为他审的是"这样做对不对"，不是"写得对不对"。

为什么用 Skill 而不是 Git Hooks

维度 Skill + 检查点 ✅ Git Hooks (Husky) ❌
灵活性 AI 理解上下文，智能判断 写死的 shell 脚本
可跳过 不需要跳过，检查点自动判断 --no-verify 绕过
团队维护 skill 在 CLAUDE.md 里定义 每人要装 husky + 配置
适用场景 PR 描述、文档同步（需要理解） 格式化、lint（机械检查）
重复运行 检查点去重，同 commit 跳过 每次都跑，浪费时间
AI 配置文件体系
CLAUDE.md 是最高 ROI 投资
文件 受众 内容 提交 Git
AGENTS.md 所有 AI 工具 项目概览、阅读顺序、红线 ✅ 是
CLAUDE.md Claude Code 架构细节、命令速查、编码原则 ✅ 是
.cursor/rules/*.mdc Cursor 项目规则（从 CLAUDE.md 派生） ✅ 是
.github/copilot-instructions.md Copilot 项目指令（从 CLAUDE.md 派生） ✅ 是
.claude/settings.json Claude Code hooks、权限白名单 ✅ 是
.claude/settings.local.json Claude Code 个人偏好 ❌ 否
.claude/.skill-checkpoints Claude Code Skill 运行记录（pre-push 检查点） ❌ 否（自动 gitignore）
